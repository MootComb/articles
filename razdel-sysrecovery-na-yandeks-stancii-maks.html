Раздел sysrecovery на Яндекс Станции Макс

В таблице разделов Яндекс Станции Макс без ZigBee (YNDX-0008) есть раздел sysrecovery размером 1,5 ГБ.

Где он используется

Всё описано переменными окружения в U-Boot, а именно скриптом sysrecovery_check, вызываемым из preboot:

preboot=run true;run bcb_cmd; run factory_reset_poweroff_protect;run start_boot_animation;run init_display;**run sysrecovery_check**;run upgrade_check;run storeargs;bcb uboot-command;run switch_bootmode;

Вот как работает sysrecovery_check:

sysrecovery_check=if test ${factory_mode} -eq 1; then
    echo Factory mode! Skipp recovery checking!;
  else
    get_reset_gpio RESET_GPIO;
    echo RESET GPIO = ${RESET_GPIO};
    sysrecovery=1;
    for i in 1 2 3 4 5; do
      if test ${sysrecovery} -eq 1; then
        if gpio input ${RESET_GPIO}; then sleep 1;
        else sysrecovery=0; fi;
      fi;
    done;
    if test ${sysrecovery} -eq 1; then
      if gpio input ${RESET_GPIO}; then
        setenv led_ring_brightness 255;
        led_ring scp pause;
        led_ring scp recovery;
        amlmmc erase cache;
        amlmmc erase data;
        amlmmc erase misc;
        aml_sysrecovery 1;
      fi;
    fi;
  fi;

Что это значит:

  1. get_reset_gpio RESET_GPIO определяет GPIO, к которому привязана кнопка отключения микрофона.
  2. Цикл из пяти повторений с интервалом 1 с: если GPIO читается как 0 (нажат), выполняется sleep 1, иначе sysrecovery=0 и цикл прерывается. Таким образом, кнопку нужно удерживать в течение всех пяти проверок.
  3. Ещё одна проверка gpio input после цикла.
  4. После этого запускается восстановление.

Поскольку sysrecovery_check стоит до bcb uboot-command в preboot, повреждённый misc не мешает входу в режим восстановления.

Что содержит раздел

В sysrecovery лежит набор разделов, описанный секцией [burn_parts]:

[burn_parts]
burn_num         = 10
burn_part0       = _aml_dtb
burn_part1       = boot
burn_part2       = dtbo
burn_part3       = logo
burn_part4       = odm
burn_part5       = product
burn_part6       = recovery
burn_part7       = system
burn_part8       = vbmeta
burn_part9       = vendor
#РазделФорматНазначение
0_aml_dtbnormalDevice tree (мульти-DTB, выбирается по hw_rev)
1bootnormalЯдро + initrd
2dtbonormalDevice tree
3logonormalЛоготип
4odmsparseODM-раздел
5productsparseProduct-раздел
6recoverynormalRecovery
7systemsparseСистемный раздел
8vbmetanormalМетаданные AVB2 (Verified Boot)
9vendorsparseVendor-раздел

В логе видно, что объём образа 1491 МБ.

Что стирается и прошивается

Перед вызовом aml_sysrecovery 1 скрипт стирает три раздела:

amlmmc erase cache;
amlmmc erase data;
amlmmc erase misc;

Дальше aml_sysrecovery последовательно, по одному, прошивает 10 разделов по порядку из sysrecovery (_aml_dtb, boot, dtbo, logo, odm, product, recovery, system, vbmeta, vendor). Для каждого в логе виден полный цикл:

[MSG]=====>To burn part [boot]
[MSG]flash LOGIC partCap 0x1000000B
[MSG]Down(store) part(boot) sz(0x1000000) fmt(normal)
[MSG]Burn Start...
[MSG]Burn complete
[MSG]Verify Start...
[MSG]To verify part boot in fmt normal
[MSG]Verify End
[MSG]VERIFY OK

Для каждого раздела выполняется запись и верификация, после чего происходит переход к следующему разделу. odm, product, system и vendor пишутся в sparse-формате, а _aml_dtb, boot, dtbo, logo, recovery и vbmeta в normal. _aml_dtb пишется со смещением 0x13ffd20 через dtb_write, также обновляется и его служебная копия.

После записи последнего раздела (vendor):

[MSG]To clear data part[data]
[MSG]partCap 0x85aMB, ClearSz=2Mb

[MSG]=====>To burn part [bootloader]
[MSG]Down(store) part(bootloader) sz(0x17a370) fmt(normal)
...
mmc switch to boot0 success
mmc switch to boot1 success
mmc switch to user success
[MSG]Burn complete
[MSG]VERIFY OK
[MSG]Set upgrade_step to 1
Saving Environment to aml-storage...
mmc env offset: 0x4d400000
Writing to MMC(1)... done
[MSG]to close image
[MSG]======sdc burn SUCCESS.
reboot mode: normal

Раздел bootloader пишется не в пользовательскую область, а в boot0/boot1 eMMC (mmc switch to boot0/boot1 success). Это отдельный шаг, выполняемый после основного списка разделов. После успешной записи выставляется upgrade_step = 1.

Зачем это нужно

  • Откатиться на заводскую прошивку
  • Сбросить данные (очистить data)

Когда сброс не поможет

  • Если устройство не доходит до U-Boot.
  • Повреждён раздел env.
  • Повреждены эти переменные в env: factory_mode, bootcmd, preboot или sysrecovery_check.
